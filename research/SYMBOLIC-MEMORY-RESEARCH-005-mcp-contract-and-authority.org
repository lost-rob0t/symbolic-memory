#+status: PENDING-HUMAN-REVIEW
#+repo: lost-rob0t/symbolic-memory
#+date: 2026-08-29

* Research question

How should the symbolic-memory MCP server expose memory to LLMs through a very small native tool API while preserving Prolog-first semantics, scoped authority, full-corpus long-term recall, lossless source memory, and safe forgetting?

This revision reconciles the MCP contract with the human-approved decisions in =SYMBOLIC-MEMORY-RESEARCH-011=.

This document remains research only. It does not approve implementation.

* Research conclusion

The ordinary LLM-facing API SHOULD expose six native tools:

#+begin_example
memory_remember
memory_search
memory_recall
memory_get
memory_forget
memory_explain
#+end_example

The LLM should not need to:

- write Prolog;
- understand internal predicates;
- construct query ASTs for normal use;
- choose indexes or retrieval backends;
- open a context handle before ordinary operations;
- manually merge project/session/global memory;
- reason about internal lifecycle predicates;
- reconstruct natural-language memory from symbolic facts.

Prolog remains the semantic and authorization engine underneath these tools.

* API principle

The server should use the host's native tool mechanism directly.

For MCP clients, these are ordinary MCP tools with simple JSON Schema inputs and structured outputs.

The design target is that an LLM can learn the common API from the tool names and schemas alone.

The model-facing layer should look like a normal tool API, not like a Prolog REPL.

* Golden-path tool surface

** =memory_remember=

Purpose: save something worth remembering while preserving the original natural-language text losslessly.

Minimal call:

#+begin_src json
{
  "memory": "Use Prolog as the authority for this project."
}
#+end_src

Useful optional arguments MAY include:

- =scope=: =session=, =project=, =global=;
- =lifetime=: =short_term=, =long_term=, or =auto=;
- =kind=: =auto=, =fact=, =episode=, =preference=, =procedure=, =text=;
- =importance=;
- =source= when the caller has useful provenance information.

Defaults should bind to the current project when one is known, otherwise the current session. Failure to resolve project identity MUST NOT silently become a global write.

The server preserves the exact source text and may derive zero or more symbolic projections internally.

Symbolic projection MUST NOT replace the original source memory.

** =memory_search=

Purpose: deliberately search the full authorized long-term memory corpus.

Minimal call:

#+begin_src json
{
  "query": "What decisions did we make about long-term memory?"
}
#+end_src

Search is for corpus exploration, discovery, historical lookup, auditing, and explicit long-term recall.

It may search, subject to authority:

- project long-term memories;
- permitted user/global memories;
- symbolic facts;
- lossless source prose;
- episodic/source observations;
- preferences and procedures;
- provenance and derivation edges;
- archived or superseded history when requested.

Optional arguments MAY include:

- =scope=: =current=, =project=, =global=, =all_visible=;
- =history=: boolean;
- =limit=;
- =kind=;
- =mode=: =auto=, =symbolic=, =text=, =exact=, =semantic=, =historical=.

Default =mode=auto= lets Prolog choose the retrieval plan.

The model should not need to know whether Prolog used predicate matching, full-text lookup, temporal search, graph traversal, or optional semantic/vector candidate generation.

** =memory_recall=

Purpose: compile the smallest sufficient task-ready memory packet for the active model.

=memory_recall= is intentionally distinct from =memory_search=.

#+begin_example
memory_search -> find/explore memories in the authorized corpus
memory_recall -> compile relevant memories into current model context
#+end_example

Recall defaults to symbolic memory.

The model-facing recall output MUST NOT be raw Prolog source. It should look approximately like concise Markdown while also returning structured metadata.

Example rendered content:

#+begin_example
# Recalled memory

## Project
- **Architecture · Current** — Recall is symbolic-first. [mem_91]
- **Storage · Current** — Preserve original natural-language memory losslessly. [mem_92]

## Source context
Included because the symbolic projection omits a relevant qualification.

> [mem_92] Recall symbolic memory first and include the exact source prose only when the symbols lose important context.
#+end_example

Recall SHOULD include exact lossless source prose only when the symbolic representation lacks necessary task context.

Possible source-expansion triggers include:

- projection is marked lossy or context-required;
- exact wording is requested;
- rationale, exceptions, sequence, or qualifications matter;
- contradictions require source inspection;
- trust policy requires inspecting source evidence;
- adequacy checking determines that symbolic recall is insufficient.

The prose fallback MUST come from the stored source record. It MUST NOT be reconstructed by an LLM and presented as original memory.

Recall should prominently return memory IDs so the model can use exact IDs in follow-up operations.

** =memory_get=

Purpose: inspect one known memory by ID.

#+begin_src json
{
  "id": "mem_42"
}
#+end_src

The detailed result MAY include:

- exact original source text;
- symbolic projections;
- provenance;
- temporal state;
- supersession chain;
- trust and authority metadata;
- derivation/dependency links;
- related memory IDs.

This keeps ordinary recall/search concise while preserving deep inspection.

** =memory_forget=

Purpose: stop one or more memories from influencing ordinary current recall.

The preferred model path is ID-first.

#+begin_src json
{
  "ids": ["mem_42", "mem_43"]
}
#+end_src

When the model already has memory IDs, it should use them directly instead of repeating the memory text.

Natural-language forgetting remains supported as a resolver when IDs are unknown or the user requests broad topic forgetting.

#+begin_src json
{
  "query": "memories relating to the old SQLite backend plan"
}
#+end_src

Natural-language text is not itself the mutation target.

The intended flow is:

#+begin_example
natural-language request
        ↓
Prolog forget resolver
        ↓
concrete related memory IDs
        ↓
forget lifecycle applied to those IDs
#+end_example

The resolver SHOULD consider:

1. symbolic entity/fact matches;
2. symbolic relation traversal;
3. provenance/derivation links;
4. full-text lossless source matches;
5. explicit aliases/entity normalization;
6. optional semantic/vector candidates as a fallback.

The mutation is always applied to resolved concrete IDs.

Forgetting MAY internally mean archive, invalidate, expire, demote, supersede, retract derived state, or physically delete when policy explicitly requires destructive deletion.

Dependent memories or learned rules whose only support disappears may need invalidation or recomputation rather than blind deletion.

** =memory_explain=

Purpose: explain why a memory was stored, returned, trusted, derived, superseded, or affected by forgetting.

Example:

#+begin_src json
{
  "id": "mem_42"
}
#+end_src

The response should translate Prolog proof/provenance into concise model-readable structure rather than exposing engine internals by default.

* Structured output plus model-readable content

Native tool results should be shallow and obvious.

For recall in particular, the result SHOULD contain both:

1. model-readable Markdown-like content;
2. structured metadata containing IDs and machine-usable state.

Conceptual shape:

#+begin_src json
{
  "content": "# Recalled memory\n...",
  "memories": [
    {
      "id": "mem_91",
      "scope": "project",
      "status": "current",
      "statement": "Recall is symbolic-first.",
      "source_context_included": false
    }
  ]
}
#+end_src

Detailed proof trees belong behind =memory_explain= or an explicit details flag.

* Context should normally be host-provided

The host/client should normally bind:

- principal/user;
- current project identity when known;
- current session/run identity when known;
- permitted global/shared scopes.

The model should not need to repeat project/session identity on every call.

Explicit scope/context overrides may remain available for intentional cross-scope access when authorized.

Project resolution and authorization are separate operations.

* Small API does not mean small memory

The working-memory/context packet is only a bounded attention view.

It is NOT the total memory accessible to the LLM.

The model retains explicit deliberate access to the full authorized long-term corpus through =memory_search=.

This invariant is central:

#+begin_example
                 ┌─ automatic bounded symbolic-first recall
long-term corpus ┤
                 └─ explicit full-corpus search
#+end_example

* Authority model

Simple tools must sit on top of strict scope-aware capabilities.

Candidate internal capabilities include:

#+begin_src prolog
capability(memory_read).
capability(memory_write_session).
capability(memory_write_project).
capability(memory_write_global).
capability(memory_forget).
capability(rule_propose).
capability(rule_test).
capability(rule_activate_project).
capability(rule_activate_global).
capability(memory_admin).
#+end_src

A normal model should usually receive:

- read access to permitted scopes;
- session writes;
- current-project writes;
- ordinary forgetting within its authorized scopes.

It should not automatically receive:

- arbitrary project access;
- global writes;
- global rule activation;
- audit-history deletion;
- unrestricted symbolic execution.

Trust and authority remain separate.

A trusted observation does not automatically have authority to become global policy, and a model inference must not inherit user authority simply because it derives from user text.

* Project and global isolation

Project-local memory must not leak into sibling projects through ranking or search.

Global memory is a distinct namespace, never the fallback for unresolved project identity.

Cross-project/shared memory should be explicit and separately authorized.

The Prolog domain model should enforce these invariants in addition to transport middleware.

* Advanced symbolic and rule tools

Advanced operations may exist, but they should not clutter default tool discovery.

Possible privileged tools include:

- =memory_query_symbolic=;
- =memory_rule_propose=;
- =memory_rule_test=;
- =memory_rule_activate=;
- =memory_rule_rollback=;
- audit/repair/benchmark/optimizer administration tools.

No unrestricted model-facing =assertz/1=, =retract/1=, =consult/1=, shell, file, or network execution should be exposed as ordinary memory API.

Tool discovery should follow least privilege: models should ideally see only the tools they are allowed and expected to use.

* Audit requirements

Every mutating operation should record internally:

- caller/principal;
- tool/action;
- resolved scope;
- target memory IDs;
- source/provenance;
- timestamp;
- previous/new version where applicable;
- authorization/policy result;
- resolved ID set for natural-language forgetting.

The model should not need to provide this bookkeeping manually.

* Revised research recommendation

The v1 ordinary model-facing surface should therefore be:

1. =memory_remember=;
2. =memory_search=;
3. =memory_recall=;
4. =memory_get=;
5. =memory_forget=;
6. =memory_explain=.

The key semantics are now:

- native tool calls, not Prolog syntax;
- lossless natural-language source retained on write;
- symbolic-first recall;
- exact prose fallback only when symbolic context is insufficient;
- search over the full authorized long-term corpus;
- recall distinct from search;
- prominent stable memory IDs;
- ID-first model forgetting;
- natural-language forgetting resolved by Prolog to concrete related IDs;
- strict project/global authority underneath the simple API.

* Remaining open questions

The major unresolved design questions are now narrower:

- Should explicit =memory_remember= default to durable long-term capture, or enter short-term/raw capture and rely on consolidation policy?
- What exact adequacy policy decides when recall expands a symbolic memory into lossless prose?
- How much automatic symbolic projection should happen synchronously on =memory_remember=?
- How should different MCP hosts bind current project/session identity consistently?
- How far may dependency closure travel during broad natural-language forgetting before requiring stronger confidence or explicit confirmation?
- Should advanced =memory_query_symbolic= live in the same server with capability-gated discovery or in a separate expert surface?

These questions do not alter the revised six-tool API split, but they should be resolved before implementation details are frozen.
