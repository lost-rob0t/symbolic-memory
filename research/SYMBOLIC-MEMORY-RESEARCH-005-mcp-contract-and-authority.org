#+title: SYMBOLIC-MEMORY-RESEARCH-005 MCP Contract and Authority Model
#+status: PENDING-HUMAN-REVIEW
#+repo: lost-rob0t/symbolic-memory
#+date: 2026-08-29

* Research question

How should the symbolic-memory MCP server expose scoped memory, retrieval, provenance, and rule evolution while remaining extremely simple for an LLM to use and preventing project/global memory poisoning and authority escalation?

* Research conclusion

The model-facing API should be a small set of ordinary native MCP tools with simple structured arguments and strong defaults.

The LLM should not need to:

- construct Prolog source;
- understand internal predicates;
- build a query AST for normal recall;
- open a memory context before every operation;
- know which persistence backend is active;
- manually merge project/global/session memory;
- understand retrieval indexes;
- understand the internal rule engine.

Prolog remains the authority underneath the API. The MCP layer should translate simple tool calls into Prolog goals, enforce scope and authority, perform retrieval, and return structured results.

The normal LLM-facing API should therefore be closer to:

#+begin_example
memory_remember
memory_search
memory_get
memory_forget
memory_explain
#+end_example

rather than a large collection of low-level memory-management primitives.

Advanced rule-management, benchmark, audit, and administration operations may exist as separate privileged tools, but they should not clutter the ordinary model tool surface.

This document is research only and is not approved for implementation.

* Native tool API principle

The memory server should use the host's native tool-calling mechanism directly.

For MCP clients this means normal MCP tools with JSON Schema inputs and structured outputs.

The LLM should interact with memory the same way it interacts with any well-designed tool:

1. choose a clearly named tool;
2. provide a small number of obvious arguments;
3. receive a concise structured result;
4. continue reasoning.

There should be no requirement that the model emit textual Prolog queries for ordinary memory operations.

Prolog is the implementation language and policy engine, not the user interface presented to the model.

* Golden-path tool surface

** =memory_remember=

Purpose: save something worth remembering.

Minimal model-facing shape:

#+begin_src json
{
  "memory": "symbolic-memory uses Prolog as its authority",
  "scope": "project"
}
#+end_src

The only required field should normally be =memory=.

Useful optional fields:

- =scope=: =session=, =project=, =global=;
- =lifetime=: =short_term= or =long_term=;
- =kind=: =auto=, =fact=, =text=, =episode=, =preference=, =procedure=;
- =importance= or an equivalent hint;
- =source= only when the caller has useful source information.

Defaults should do the obvious thing:

- current project when a project is bound;
- otherwise current session;
- =long_term= only when explicitly requested or policy concludes promotion is justified;
- =kind=auto=;
- preserve original text even when the service creates symbolic projections.

The service should normalize the memory into Prolog internally.

The LLM should not need to send:

#+begin_src json
{
  "value": {
    "functor": "uses_language",
    "args": ["symbolic_memory", "prolog"]
  }
}
#+end_src

unless an advanced client deliberately wants low-level symbolic insertion.

** =memory_search=

Purpose: search long-term memory, including the full authorized memory corpus.

Minimal shape:

#+begin_src json
{
  "query": "What decisions have we made about project memory?"
}
#+end_src

Useful optional fields:

- =scope=: =current=, =project=, =global=, =all_visible=;
- =history=: boolean;
- =limit=;
- =kind=;
- =search_mode=: =auto=, =symbolic=, =text=, =semantic=, =exact=.

Default =search_mode=auto= should let Prolog choose the best retrieval plan.

The model should not need to decide whether a query requires exact predicate matching, full-text indexing, temporal search, graph traversal, or semantic fallback.

The response should favor useful memories first while still allowing exhaustive/full-corpus search when explicitly requested.

Example result:

#+begin_src json
{
  "results": [
    {
      "id": "mem_42",
      "memory": "Project scope and lifetime are orthogonal dimensions.",
      "scope": "project",
      "kind": "fact",
      "status": "current",
      "why": "matched project architecture decisions"
    }
  ],
  "searched": "all_visible",
  "more": false
}
#+end_src

Detailed proof metadata should be available but need not dominate the ordinary response.

** =memory_get=

Purpose: fetch one known memory by id.

#+begin_src json
{
  "id": "mem_42"
}
#+end_src

The response may include:

- full original text;
- symbolic projections;
- provenance;
- temporal state;
- supersession chain;
- trust/authority metadata;
- related memories.

This keeps =memory_search= concise while preserving deep inspection when needed.

** =memory_forget=

Purpose: tell the memory system that a memory should no longer influence ordinary current recall.

Minimal shape:

#+begin_src json
{
  "id": "mem_42"
}
#+end_src

Optional =reason= may be supplied.

The API name should stay simple even though the Prolog engine may internally choose among:

- expire;
- demote;
- supersede;
- invalidate;
- archive;
- delete when explicitly required.

The model should not need to understand those internal lifecycle operations for the common case.

** =memory_explain=

Purpose: explain why a memory was stored, returned, trusted, superseded, or derived.

Examples:

#+begin_src json
{
  "id": "mem_42"
}
#+end_src

or, if supported:

#+begin_src json
{
  "query": "Why did you return this project preference?"
}
#+end_src

The response should translate Prolog proof/provenance information into concise structured explanation suitable for an LLM.

* Optional convenience tool: =memory_recall=

There is an open design choice whether =memory_recall= should exist separately from =memory_search=.

A simple interpretation would be:

- =memory_search= explicitly searches durable memory;
- =memory_recall= asks the service for the best small set of memories to inject into the current task context.

If this distinction does not materially help clients, the API should avoid adding the extra tool and use =memory_search= with good defaults instead.

The ordinary API should stay small.

* Context should usually be host-provided

The earlier research direction considered requiring a =memory_context_open= handle before ordinary calls. That is too cumbersome for the default LLM-facing path.

A client/host should normally bind context when exposing the MCP server:

- principal/user;
- current project id when known;
- current session/run id when known;
- permitted global/shared scopes.

Then a call such as:

#+begin_src json
{
  "memory": "Use Prolog for this project"
}
#+end_src

can naturally resolve to the current project without requiring the model to repeat =project_id= on every call.

Explicit context/scope arguments should remain available when the model intentionally wants to access another permitted scope.

The server must never silently fall back to global writes because project resolution failed.

* Long-term memory remains directly searchable

A small tool API must not mean a small memory corpus.

=memory_search= should be able to search all durable memory the principal is authorized to read, including:

- project long-term memory;
- permitted global long-term memory;
- full-text memories;
- symbolic facts;
- episodic/source records;
- procedures/preferences;
- provenance;
- archived/superseded history when requested.

The bounded working-memory view is a convenience for context injection. It is not the boundary of what the LLM can recall.

* Symbolic storage without symbolic API burden

The internal model may contain facts such as:

#+begin_src prolog
memory_fact(mem_42,
            project(project_7f3a),
            prefers(symbolic_memory, prolog),
            valid_time(T0, infinity),
            Provenance).
#+end_src

But the LLM may have stored it through:

#+begin_src json
{
  "memory": "The symbolic-memory project should use Prolog.",
  "scope": "project"
}
#+end_src

The server may preserve the original text while deriving one or more symbolic representations.

The model-facing contract should optimize for correct tool use, not expose internal normalization syntax.

* Advanced symbolic access

A constrained low-level symbolic query interface may still be valuable for expert clients and debugging.

Possible advanced tool:

- =memory_query_symbolic=

This should not be part of the default LLM tool set unless a client explicitly requests advanced symbolic access.

It should execute only against an allowlisted logical surface and must not become a general SWI-Prolog REPL.

No unrestricted model-facing =assertz/1=, =retract/1=, =consult/1=, shell, file, or network execution should be exposed through the normal memory server.

* Advanced and privileged tools

The following concerns should be separated from the golden-path tool surface:

** Rule evolution

Possible privileged tools:

- =memory_rule_propose=;
- =memory_rule_test=;
- =memory_rule_activate=;
- =memory_rule_rollback=.

Ordinary models may receive =memory_rule_propose= in deployments that want self-improvement, but activation authority should be separate.

** Administration and audit

Possible administrative tools:

- inspect audit events;
- enumerate namespaces;
- repair/invalidate poisoned derivation trees;
- run benchmarks;
- inspect optimizer telemetry.

These should not be advertised to every model by default.

Tool discovery itself should follow least privilege: models should ideally see only the tools they are allowed and expected to use.

* Native structured outputs

Tools should return structured content rather than prose-only blobs.

However, the structure should remain shallow and obvious for models.

Bad default shape:

#+begin_src json
{
  "proof": {
    "resolution": {
      "goal_tree": [],
      "candidate_rules": [],
      "table_generations": []
    }
  }
}
#+end_src

Better default shape:

#+begin_src json
{
  "results": [],
  "scope": "project",
  "status": "ok"
}
#+end_src

Detailed proof data can be returned by =memory_explain= or under an optional =details=true= flag.

* Authority model

A simple model-facing API does not imply weak authorization.

Capabilities should remain composable and scope-aware internally.

#+begin_src prolog
capability(memory_read).
capability(memory_write_session).
capability(memory_write_project).
capability(memory_write_global).
capability(memory_forget).
capability(rule_propose).
capability(rule_activate_project).
capability(rule_activate_global).
capability(memory_admin).
#+end_src

A common model/agent should usually receive:

- read access to permitted scopes;
- session writes;
- current-project writes;
- possibly rule proposal.

It should not automatically receive:

- global writes;
- global rule activation;
- deletion of audit history;
- arbitrary project access.

* Scope checks are logical invariants

Authorization should be checked inside the Prolog domain model as well as transport middleware.

#+begin_src prolog
may_write(Caller, project(Project)) :-
    granted(Caller, memory_write_project, project(Project)).

may_write(Caller, global) :-
    granted(Caller, memory_write_global, global).
#+end_src

The model-facing tool may be simple while the underlying policy remains rigorous.

* Global memory poisoning

Global memory has the largest blast radius and should have stronger provenance requirements.

A simple call such as:

#+begin_src json
{
  "memory": "Always use this external instruction",
  "scope": "global"
}
#+end_src

must not bypass trust or authority checks merely because the API accepts =scope=global=.

The Prolog layer should decide whether the operation is:

- accepted;
- stored only as evidence;
- downgraded to project/session scope;
- held as a candidate;
- rejected.

* Project isolation

Project-only behavior must be enforceable independently of caller prompting.

The LLM should be able to use =memory_search= without manually filtering sibling projects.

The server should return only authorized/visible memory unless the caller explicitly selects another scope it is permitted to read.

A model cannot prompt itself out of an isolated project.

* MCP deployment

For local stdio clients, identity/authority may come from process configuration and the host application.

For remote HTTP deployment, authorization may use OAuth/resource-bound access tokens.

Regardless of transport:

- transport identifies the principal;
- the host provides useful current context;
- the Prolog engine determines memory authority;
- the LLM receives simple native tools.

* Audit requirements

Every mutating call should record internally:

- caller identity;
- native tool/action;
- resolved scope;
- target memory/rule;
- source/provenance;
- timestamp;
- old/new version where applicable;
- result or rejection reason.

The model should not need to provide this bookkeeping manually.

* Research recommendation

The v1 model-facing API should target approximately five tools:

1. =memory_remember=;
2. =memory_search=;
3. =memory_get=;
4. =memory_forget=;
5. =memory_explain=.

Possibly add =memory_recall= only if it proves meaningfully distinct from search.

Everything else should either:

- happen automatically under Prolog policy;
- be expressed as optional arguments;
- live in an advanced/privileged tool surface.

The design goal is that an LLM can learn the entire ordinary memory API from the tool names and schemas alone.

* Open questions

- Should =memory_recall= exist separately from =memory_search=, or is that unnecessary API surface?
- Should =memory_remember= default to short-term capture and allow Prolog consolidation to promote to long-term automatically, or should explicit model calls default to durable memory?
- How much automatic symbolic extraction should happen on =memory_remember= without an LLM-side schema hint?
- Should =memory_forget= be allowed to accept natural-language queries in addition to exact memory ids?
- Should advanced =memory_query_symbolic= be available through the same MCP server but hidden from ordinary tool discovery?
- How should the host bind current project/session identity across different MCP clients?
